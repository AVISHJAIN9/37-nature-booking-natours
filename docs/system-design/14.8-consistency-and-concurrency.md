# 14.8: Consistency And Concurrency

## 1. Overview & Context in Wanderly
This module analyzes `consistency-and-concurrency` specifically applied to the high-performance Wanderly frontend and its evolution toward a globally distributed, high-traffic reservation platform.

## 2. Technical Evaluation & Comparison
| Strategy / Architecture | Chosen Implementation | Alternative A | Alternative B | Trade-Off Accepted |
|---|---|---|---|---|
| **Delivery Model** | Static Asset Edge Caching | Server-Side Rendering (SSR) | Single Page App (SPA Client Hydration) | Zero runtime compute overhead accepted over dynamic personalization. |
| **Compute Location** | Global CDN Edge (Cloudflare/CloudFront) | Origin Node.js Cluster | Kubernetes Ingress Controller | Sub-millisecond TTFB globally at negligible operating cost. |

## 3. Scalability & Failure Modes
- **At 10x Scale**: 100% served out of browser cache and CDN edges without origin strain.
- **At 100x Scale**: Static origin egress spikes; mitigated by configuring stale-while-revalidate and aggressive cache headers (`max-age=31536000, immutable`).
- **At 1000x Scale**: Egress bandwidth becomes primary cloud cost driver; mitigated by WebP/AVIF asset compression and HTTP/3 multiplexing.

## 4. Spoken 30-Second Interview Response
> "For consistency and concurrency, I designed Wanderly's architecture around immutable static asset edge delivery. Because all interactive states are computed directly inside the browser's GPU compositor using CSS state machines, our origin server performs zero runtime rendering. At scale, the application achieves a 99% CDN cache hit ratio, delivering sub-50-millisecond load times worldwide at fractional hosting costs."
